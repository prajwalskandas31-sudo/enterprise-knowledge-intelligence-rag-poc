# Snowflake Cortex Analyst Setup & Implementation Guide ❄️🧠

A step-by-step guide to setting up, configuring, and deploying **Snowflake Cortex Analyst** in your own Snowflake environment to power natural language data analytics with automated SQL generation and tabular results.

---

## 📋 Overview & Prerequisites

Snowflake Cortex Analyst converts natural language business questions into precise SQL queries using a **Semantic Model Specification (YAML)** defined over your Snowflake data warehouse tables.

### Prerequisites Checklist:
1. **Snowflake Account**: Enterprise Edition or higher in a supported Cortex region (AWS, Azure, or GCP).
2. **User Privileges**:
   - `ACCOUNTADMIN` or a custom role with `CREATE DATABASE`, `CREATE SCHEMA`, `CREATE TABLE`, `CREATE STAGE`.
   - `GRANT DATABASE ROLE SNOWFLAKE.CORTEX_USER TO ROLE <YOUR_ROLE>;`
3. **Snowsight UI / SnowSQL CLI**: Access to Snowflake Web UI to execute DDL scripts and generate tokens.

## 🛠️ Step 1: Provision Snowflake Database, Schema & Sample Data Table

Run the following SQL commands in Snowsight worksheet to set up the data foundation:

```sql

CREATE WAREHOUSE IF NOT EXISTS COMPUTE_WH 
  WITH WAREHOUSE_SIZE = 'XSMALL' 
  AUTO_SUSPEND = 60 
  AUTO_RESUME = TRUE;

CREATE DATABASE IF NOT EXISTS FDP_CORTEX_POC;
CREATE SCHEMA IF NOT EXISTS FDP_CORTEX_POC.RAW_DATA;

USE WAREHOUSE COMPUTE_WH;
USE DATABASE FDP_CORTEX_POC;
USE SCHEMA RAW_DATA;

-- 2. Create CUSTOMERS Analytics Table
CREATE OR REPLACE TABLE CUSTOMERS (
    customer_id INT PRIMARY KEY,
    customer_name VARCHAR(100),
    city VARCHAR(50),
    state VARCHAR(50),

    annual_revenue DECIMAL(15,2),
```

## 📦 Step 2: Create Internal Snowflake Stage for Semantic YAML

Snowflake Cortex Analyst references a Semantic YAML model file stored inside a Snowflake Stage:

```sql
-- Create Stage for Cortex Analyst Semantic YAML Specifications
CREATE OR REPLACE STAGE FDP_CORTEX_POC.RAW_DATA.CORTEX_ANALYST_STAGE
    DIRECTORY = (ENABLE = TRUE)
    FILE_FORMAT = (TYPE = 'YAML');
```

---

## 📄 Step 3: Define the Semantic Model Specification (YAML)

Create a local YAML file named `customer_analytics.yaml`. This file defines table relationships, dimensions, measures, synomyms, and verified queries for Cortex Analyst.

```yaml
name: customer_analytics
description: "Semantic data model for enterprise customer demographics and annual revenue analytics."

tables:
  - name: CUSTOMERS
    base_table:
      database: FDP_CORTEX_POC
      schema: RAW_DATA
      table: CUSTOMERS
    description: "Contains customer profiles, location details, industry classifications, and annual revenue data."
    
    dimensions:
      - name: customer_id
        expr: customer_id
        data_type: NUMBER
        description: "Unique integer identifier for each enterprise customer."
        synonyms: ["client id", "account id", "customer number"]

      - name: customer_name
        expr: customer_name
        data_type: TEXT
        description: "Official registered business name of the customer."
        synonyms: ["company name", "client name", "business name"]

      - name: city
        expr: city
        data_type: TEXT
        description: "Metropolitan city where the customer headquarters is located."
        synonyms: ["location", "town", "headquarters city"]

      - name: state
        expr: state
        data_type: TEXT
        description: "State or province of customer operations."

      - name: industry
        expr: industry
        data_type: TEXT
        description: "Primary industry vertical of the customer."
        synonyms: ["sector", "business type", "vertical"]

    measures:
      - name: annual_revenue
        expr: annual_revenue
        data_type: NUMBER
        description: "Total annual revenue generated by the customer in USD."
        synonyms: ["revenue", "sales", "earnings", "turnover"]
        default_aggregate: SUM

    time_dimensions:
      - name: created_date
        expr: created_date
        data_type: DATE
        description: "Date when the customer account was onboarded."

verified_queries:
  - name: "Highest average revenue city"
    question: "Which city has the highest average customer revenue?"
    sql: "SELECT city, AVG(annual_revenue) AS avg_annual_revenue FROM FDP_CORTEX_POC.RAW_DATA.CUSTOMERS GROUP BY city ORDER BY avg_annual_revenue DESC LIMIT 1;"

  - name: "Total customer annual revenue"
    question: "What is the total annual revenue across all customers?"
    sql: "SELECT MIN(customer_id) AS start_customer_id, MAX(customer_id) AS end_customer_id, SUM(annual_revenue) AS total_annual_revenue FROM FDP_CORTEX_POC.RAW_DATA.CUSTOMERS;"
```

## ⬆️ Step 4: Upload the Semantic YAML File to Snowflake Stage

Upload `customer_analytics.yaml` to the stage `@FDP_CORTEX_POC.RAW_DATA.CORTEX_ANALYST_STAGE`.

### Option A: Via Snowsight UI
1. Open **Snowsight** -> **Data** -> **Databases** -> `FDP_CORTEX_POC` -> `RAW_DATA` -> **Stages**.
2. Click `CORTEX_ANALYST_STAGE`.
3. Click **+ Files** in top right and upload `customer_analytics.yaml`.

### Option B: Via SnowSQL CLI
```sql
PUT file://./customer_analytics.yaml @FDP_CORTEX_POC.RAW_DATA.CORTEX_ANALYST_STAGE AUTO_COMPRESS=FALSE OVERWRITE=TRUE;
```

## 🔑 Step 5: Generate Programmatic Access Token (PAT)

To allow the FastAPI application to query Snowflake Cortex REST APIs programmatically:

1. In Snowsight UI, click your **User Profile** (bottom left corner).
2. Select **My Profile** -> **Security**.
3. Under **Programmatic Access Tokens**, click **Generate Token**.
4. Set token scope to `PROGRAMMATIC_ACCESS_TOKEN` and copy the generated token string.

## 💡 Best Practices for Enterprise Semantic Modeling

1. **Rich Column Descriptions**: Add clear descriptions for every dimension and measure. Cortex Analyst uses LLM reasoning over these descriptions to match intent.
2. **Comprehensive Synonyms**: Include domain-specific terminology (e.g. mapping `"turnover"` or `"sales"` to `annual_revenue`).
3. **Verified Query Repository (VQR)**: Add 5–10 benchmark verified queries to the `verified_queries` block in YAML. Cortex Analyst matches exact user intent against VQRs for 100% precision.
4. **Data Aggregations**: Explicitly define `default_aggregate` (`SUM`, `AVG`, `COUNT`) on measure fields.
